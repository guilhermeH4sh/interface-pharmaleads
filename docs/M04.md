Implementação do piloto concluída para revisão em 24/10/2026; aceite humano pendente.
Artefato de implantação validado localmente. Hospedagem ainda não definida pelo usuário;

## Armazenamento

O catálogo agora é o JSON versionado
`packages/backend/src/pharmaleads/domain/source_policy/catalog.json`, distribuído
dentro do pacote Python. A configuração inicial `bootstrap-1` não aprova nenhuma
fonte e não concede nenhuma permissão.

Não existe dependência SQLite no catálogo, criação de arquivo de banco, gravação
de configuração pela aplicação nem necessidade de disco persistente para o catálogo.
Os dados de leads continuam destinados exclusivamente a `public.pharmaleads`.
Nenhuma tabela ou linha técnica é criada no Supabase.

Por padrão, o carregamento usa os recursos do pacote, independentemente do diretório
de trabalho. `PHARMALEADS_SOURCE_POLICY_PATH` é um override opcional para um JSON
publicado pelo responsável da implantação. A aplicação apenas lê esse arquivo;
se o override estiver ausente ou inválido, falha em vez de usar outro catálogo.
Quem tinha essa variável apontando para SQLite deve removê-la ou apontá-la para JSON.

## Estrutura e publicação

- `schema_version`: versão do formato, atualmente 1.
- `revision`: identificador não vazio da configuração publicada.
- `sources`: metadados de fontes, licença, termos, finalidade, aprovação e vigência.
- `policies`: revisões por fonte/campo/ação; versão mais recente prevalece.
- `history`: registro declarativo de revisões, com fonte, revisão, autor, data e motivo.

O carregador rejeita JSON inválido, chaves repetidas, schema desconhecido, campos
desconhecidos, fontes duplicadas, políticas órfãs, revisões duplicadas e fontes
aprovadas sem metadados de aprovação. Limite de configuração: 2 MB.
Mensagens de erro não reproduzem conteúdo ou caminhos de configuração.

Alterar fontes, aprovação, revogação e políticas exige revisar o arquivo e publicar
uma configuração nova. Não há edição pelo painel/API. O histórico é declarativo
e acompanha a configuração e o histórico Git; não é auditoria operacional imutável.

Cada consulta e cada fronteira de coleta/gravação relê e valida a configuração.
Atualização de arquivo externo deve ser atômica; todas as instâncias da API e dos
workers precisam receber a mesma revisão. Uma revogação em produção exige publicação
coordenada; não há distribuição automática nem garantia de revogação instantânea
entre máquinas. Operação externa já em andamento não é desfeita retroativamente.

## API somente leitura

| Método | Rota | Escopo |
|---|---|---|
| GET | `/v1/sources` | `sources:read` |
| GET | `/v1/sources/{source_id}/policies` | `sources:read` |
| GET | `/v1/sources/{source_id}/history` | `sources:manage` |

Rotas POST de cadastro, alteração de estado e criação de políticas foram removidas.
Admin consulta fontes, políticas e histórico; operador consulta fontes e políticas.
Os controles JWT e a origem dos papéis permanecem no M03.

## Fronteiras de coleta e persistência

`adapters.py` define capacidades, versão, origem, cursor, checkpoint e observações.
`collect` verifica antes de buscar e antes de devolver; `persist` verifica antes
do sink, inclusive quando ele representa staging/log persistente.
Adaptadores não podem gravar payloads por conta própria.

O importador CSV usa a mesma configuração antes de cada requisição remota.
`--source ID` / `-Source ID` continua necessário para escrita, além das travas
operacionais anteriores. GET de existência exige coleta de `id` e `cnpj`;
POST/PATCH exige persistência para cada campo enviado, inclusive `updated_at`.
Dry-run continua sem rede. Não houve escrita real no Supabase nesta alteração.
